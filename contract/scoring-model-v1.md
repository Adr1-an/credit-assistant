# 1. Нормативность, источники, объекты и точность

- Источник полей: contract/mocks-contract.md (ЕГРИП, налоги, БКИ, ФССП,
  банкротство, паспорт, CSV), contract/openapi.yaml (ScoreFactor, Score,
  StatementSummary, GoalsData), contract/industries.json и
  scoring-clarifications.md.

- Операционные категории поступлений CUSTOMER/ACQUIRING/OTHER_IN и
  подсчёт месяцев берём ТОЛЬКО из утверждённого mocks-contract.md. ИИ,
  классифицировавший строку, не влияет на скоринг.

- ScoreFactor: code, block, points, maxPoints, reason. Score: total,
  zone, factors, flags. Выдача клиенту внутренней суммы баллов не
  предусмотрена.

- Все оценки определены на evaluationDate = календарную дату сервера при
  скоринге; в демонстрационных тестах evaluationDate = 2026-10-24.
  Текущий месяц не анализируется.

- Финансовые суммы в рублях; дата YYYY-MM-DD; доли считаем как
  рациональные числа/Decimal без предварительного округления, границы
  сравниваем точно. Для отображения процента округляем ROUND_HALF_UP до
  1 десятичного знака; на выбор балльного диапазона это не влияет.

- Итог Score.total = сумма points у факторов; maxPoints в одном списке
  факторов = 100. points — целое 0…maxPoints. Дедупликацию обстоятельств
  делаем по code, не начисляем дополнительный глобальный штраф поверх
  факторов.

Для STOP до submit или для недоступного внешнего сервиса Score не
формируется: нельзя возвращать выдуманное
{total:0,zone:RED,factors:\[\]} как измеренный риск. При STOP статус
REJECTED, красный маршрут; при 503 статус CHECKING без зоны. Если нужен
балл для интерфейса, необходимо отдельно менять API, чего здесь не
делаем.

# 3. Дополнительные точные условия для факторов

## 3.1. BUSINESS: календарь и расчёты

- Окно: 12 последних завершённых календарных месяцев. monthsCovered —
  число месяцев с ≥1 валидной CSV-строкой, отсутствующие месяцы никогда
  не считаются нулевыми. Берём monthly\[\] строго по утверждённому
  mocks-contract.md.

- Фактор BUSINESS_STABILITY рассчитывается при monthsCovered ≥ 6 и R\>0
  по присутствующим месяцам. weakMonths: income_month \< 0,70×R (при
  ровно 70% месяц НЕ слабый). Если R=0, weakMonths=n, баллы по шкале 0.

- Для BUSINESS_REVENUE_TREND необходимы операции во всех шести последних
  полностью завершённых календарных месяцах (без пропусков). Сравниваем
  среднее трёх последних календарных месяцев и трёх перед ними. Если
  среднее предыдущих трёх равно 0 — 0 баллов + MANUAL; на нуль не
  делить.

- BUSINESS_CASH_BUFFER считается по R и E при наличии ≥6 месяцев. При
  R=0 фактор=0 и MANUAL. Если R\>0, отрицательная маржа допустима и даёт
  0.

- При monthsCovered 6–11 все доступные факторы рассчитываются, но
  ставится MANUAL независимо от итоговой суммы. При monthsCovered 1–5
  все BUSINESS и IDEA равны 0, MANUAL. Для ИП младше 3 полных месяцев
  применяется альтернативный блок старта независимо от наличия 1–2
  месяцев операций.

- Если доля OTHER_IN в сумме всех входящих операций \>20%, действует
  обязательный MANUAL из mocks-contract.md; возвращать клиентские
  заявления о выручке в расчёт запрещено.

## 3.2. OWNER: кредитная история, стаж, налоги

- Для OWNER_OVERDUE_HISTORY берём только кредиты loans\[\] из reportAsOf
  (не позже evaluationDate, возраст отчёта ≤30 календарных дней). Если
  источник старый, ставим MANUAL; соответствующий фактор 0 как
  неоценённый, не маскируем это под loans=\[\].

- Текущая просрочка = max(currentOverdueDays) среди ACTIVE кредитов.
  Если ≥90 — STOP, Score не создаётся. Если 1–89 —
  OWNER_OVERDUE_HISTORY=0 и MANUAL. Если её нет — максимальные
  overdues\[\].days для событий за последние 36 календарных месяцев,
  включая нижнюю границу. События старше 36 месяцев игнорируем. ≥90 дней
  в исторической просрочке → 0 и MANUAL.

- При loans=\[\] ставим 12/20 (это отсутствие подтверждённой истории, не
  сбой); для хорошей БКИ стартапа loans=\[\] недостаточно. Текущие
  запросы БКИ при обычном ИП не штрафуются дважды.

- Возраст ИП — число полных календарных месяцев: дата регистрации + N
  месяцев ≤ evaluationDate. Стартап hasBusiness=false получает
  OWNER_BUSINESS_AGE=0; terminated EGRIP при hasBusiness=true — STOP по
  ранее согласованной проверке.

- Налоги: 0 баллов и MANUAL при debtAmount\>50 000, asOf старше 30 дней,
  конфликте hasDebt/debtAmount или ошибке дат. При валидном
  hasDebt=false и debtAmount=0 — 4; при hasDebt=true и 1…50 000 — 2.
  Исторически погашенный долг не используется.

## 3.3. IDEA: оставляем 20 баллов, но не оцениваем рассказы

После исключения 6 баллов за прогноз окупаемости не нужно распределять
IDEA в OWNER или BUSINESS: 20 баллов остаются самостоятельной оценкой
подтверждённого финансового запаса. Эти факторы не используют ни
desiredAmount, ни desiredTermMonths, ни expectedBreakEvenMonths, ни
ownFunds, ни текст клиента.

IDEA_VERIFIED_DEBT_COVERAGE: если R\>0, monthsCovered≥6, F=R−E, L=∑
loans\[\].monthlyPayment по ACTIVE. Если L=0: F\>0 → 10, иначе 0. Если
L\>0: compare F/L с порогами таблицы. E уже включает списания по
кредитам, если они есть в CSV; не вычитаем L повторно. Это индикатор
запаса ПОСЛЕ расходов, отнесённого к известным кредитным обязательствам,
а не официальный банковский DSCR.

IDEA_VERIFIED_STRESS_BUFFER: при R\>0 и ≥6 месяцах считаем T =
(0,8R−E)/R×100%. Без ограничений снижаем только R на 20%, E оставляем
прежним. Это стресс-тест имеющегося денежного потока, а не проверка
проектной сметы. Если T = 0%, начисляем 3 балла. Отрицательное значение
даёт 0.

Если выписки нет, она охватывает 1–5 месяцев, или у стартапа отсутствуют
подтверждённые операционные поступления, оба фактора IDEA=0 с причиной
«Подтверждённый денежный поток для оценки отсутствует»; при неполных
данных — MANUAL, за исключением специального согласованного
авто-маршрута стартапа.

Предлагаемые 40/30/20/10 сохранены. Причина: меньше переделок API и
неизменное разделение финансовых блоков. Пересечение IDEA с BUSINESS
допустимо, но нужно учитывать: на реальных портфелях
независимость/корреляции требуют отдельной проверки.

## 3.4. INDUSTRY: только утверждённые значения JSON

Для действующего ИП берём EGRIP.okvedMain.code, для стартапа —
подтверждённый plannedOkved. Прямое совпадение с
industries\[\].okvedCode, иначе fallback ТОЛЬКО по первым двум цифрам,
если scope=RUSSIA_OKVED_2DIGIT. При отсутствии подходящей записи —
INDUSTRY=0 + MANUAL. При null росте/доле закрытий соответствующий
фактор=0+MANUAL; значения не восстанавливаются на глаз.

Дата отраслевых данных dataAsOf позднее evaluationDate = конфликт/
MANUAL; возраст \> 12 календарных месяцев = MANUAL (новое предлагаемое
допущение). Применять синтетические отраслевые цифры только в демо, это
не официальная статистика.

# 4. Альтернативный BUSINESS для стартапа / ИП младше трёх месяцев

Альтернативные коды существуют вместо обычных BUSINESS\_\*. Вместе они
имеют maxPoints=40. Данные — только БКИ; отсутствие реальных оборотов не
маскируется словами клиента.

| **ScoreFactor.code**             | **Источник и простое значение**                                               | **Строгая шкала**                                    | **max** |
|----------------------------------|-------------------------------------------------------------------------------|------------------------------------------------------|---------|
| BUSINESS_START_CREDIT_SEARCH     | БКИ requestsLast30Days — сколько обращений за месяц                           | 0–1→10; 2–3→5; 4 и более→0                           | 10      |
| BUSINESS_START_DEBT_LOAD         | БКИ sum(loans\[\].monthlyPayment) по ACTIVE — действующие ежемесячные платежи | 0→10; 1–20 000→7; 20 001–50 000→4; \>50 000→0        | 15      |
| BUSINESS_START_OPERATING_HISTORY | Подтверждённый денежный поток отсутствует или недостаточен                    | Всегда 0, так как нет ≥6 месяцев проверенной истории | 15      |

Примеры reason: «0 потерь из 10: запросов БКИ за 30 дней — 0»; «−5: нет
действующих кредитных платежей, но доход не подтверждён (10/15)»; «−15:
нет проверенной операционной истории». Последний фактор намеренно не
начисляет баллы: это явное отображение нехватки истории.

Для стартапа верхняя реально достижимая оценка по альтернативному
BUSINESS — 20/40. Даже с максимальными OWNER=24/30, IDEA=0/20,
INDUSTRY=10/10 стартап набирает не более 54 баллов. Поэтому по
утверждённому правилу автоодобрения необходима отдельная ветка GREEN,
описанная ниже. Не «дотягиваем» score.total до 80.

# 5. Зоны, блокировки GREEN и переходы статусов

| **Условие**                                                                     | **Score.zone**                                    | **Статус**                         | **Приоритет**       |
|---------------------------------------------------------------------------------|---------------------------------------------------|------------------------------------|---------------------|
| Любой достоверный STOP во время проверок                                        | Не выдаётся Score (маршрут RED)                   | REJECTED                           | 1                   |
| Любая обязательная заглушка 503 / тайм-аут                                      | Score отсутствует, зона не определена             | CHECKING / RETRY_CHECKS            | 0: ошибка получения |
| Нужен ИНН/исправление формы, внешний ответ противоречив, расчёт ещё не завершён | Score пока отсутствует                            | DRAFT или INFO_REQUESTED по стадии | До решения          |
| Стартап: все проверки пройдены, GOOD_BKI=true, сумма ≤ 200 000, нет MANUAL      | GREEN (специальное исключение даже при score\<80) | OFFER_READY                        | 2                   |
| Есть MANUAL или недостаточно проверенных данных, без STOP                       | YELLOW независимо от total                        | MANUAL_REVIEW после submit         | 3                   |
| Действующий ИП: total\<40, достаточно данных, нет MANUAL                        | RED                                               | REJECTED                           | 4                   |
| Действующий ИП: total≥80, нет MANUAL, 12 месяцев, возраст ИП≥12                 | GREEN                                             | OFFER_READY                        | 5                   |
| Все оставшиеся завершённые случаи                                               | YELLOW                                            | MANUAL_REVIEW                      | 6                   |

Под «достаточно данных» для автоотказа по баллам понимаем: ответы всех
шести обязательных сервисов получены и валидны; источник отрасли найден;
БКИ и налоги актуальны; выписка содержит 12 технически присутствующих
месяцев и доля OTHER_IN не больше 20%; нет MANUAL. Если хотя бы один
пункт не выполнен, низкий total не даёт RED автоматически.

GREEN для действующего ИП запрещён при: хотя бы одном MANUAL; ЕГРИП не
ACTIVE или возраст \<12 месяцев; 0–11 месяцев выписки; \>20% OTHER_IN;
отсутствии подтверждённой отрасли; просрочке 1–89 дней сейчас;
исполнительном производстве ACTIVE; аресте; завершённом банкротстве \<5
лет; несовпадении паспортных атрибутов; старом отчёте БКИ/ФНС; неполных
источниках. STOP даёт автоотказ.

Для стартапа условие GREEN уникально, он НЕ обязан предоставлять выписку
и иметь год регистрации. Но у него обязательны все внешние проверки,
подтверждённый паспорт, согласованный личный ИНН и не должно быть
другого MANUAL. Его итоговый балл может быть ниже 80. Score.zone здесь
обозначает маршрут предложения, а не чисто числовую категорию риска. Это
неизбежное следствие утверждённого в 0.5 правила; для будущей версии
желательно разделить riskBand и decisionRoute.

# 6. Стартап: STARTUP_AUTO_APPROVE_LIMIT и GOOD_BKI

Предлагаемое значение конфигурации сервера: STARTUP_AUTO_APPROVE_LIMIT =
200000 (целые рубли). Число — допущение команды, не лимит Альфа-Банка.
Конфигурация хранится на бэкенде, фронт не проверяет порог.

Автоматическое решение допустимо ТОЛЬКО когда выполняются ВСЕ условия:

- hasBusiness=false; личный ИНН указан; ЕГРИП возвращает 404 NOT_IP или
  TERMINATED (без ACTIVE). Все шесть источников ответили успешно;
  паспорт valid=true, holderMatch=true; нет STOP, MANUAL, конфликтов и
  просроченных внешних сведений.

- Сумма запрошенного финансирования берётся ТОЛЬКО из common.amount →
  desiredAmount (GoalsData.commonAnswers), это параметр будущего
  договора, НЕ балльный фактор. Тип — целое от 1 до 200000 включительно.
  Нет суммы / null / больше лимита → только MANUAL_REVIEW. Использование
  Estimate.total вместо запрошенной суммы для обхода лимита запрещено.

- БКИ: reportAsOf не старше 30 дней; loans\[\] непустой; хотя бы один
  кредит loans\[\].openedAt ≤ evaluationDate минус 12 календарных
  месяцев; для всех ACTIVE currentOverdueDays=0; ни в одном кредите нет
  событий overdues\[\].days\>0 с date в последних 36 календарных
  месяцах.

- БКИ: requestsLast30Days ≤ 1, сумма loans\[\].monthlyPayment по ACTIVE
  ≤ 20 000 ₽; все значения неотрицательные и даты валидные. Это полное
  техническое определение GOOD_BKI, НЕ банковская классификация.

- ФНС: hasDebt=false и debtAmount=0; ФССП: нет ACTIVE proceedings;
  банкротство inProcedure=false и отсутствует завершение в последние 5
  лет; отрасль найдена; нет общего MANUAL. Если условий нет —
  YELLOW/MANUAL_REVIEW, а при STOP — REJECTED.

- Дополнительно: правильный формат и актуальность всех ответов; если
  клиент не является ИП, OFFER_READY — модельное кредитное предложение,
  а ISSUED — только симулируемая выдача, не обещание реального
  предпринимательского кредита.

GOOD_BKI=false при loans=\[\] независимо от requestsLast30Days.
Например, пекарня без кредитной истории и с запросом на 700 000 ₽ не
может попасть в авто-маршрут по двум независимым причинам.

# 7. Нет выписки и неполная история: точные правила

| **Сценарий**                                         | **BUSINESS**                                               | **IDEA**                            | **Маршрут**                                                                            |
|------------------------------------------------------|------------------------------------------------------------|-------------------------------------|----------------------------------------------------------------------------------------|
| ИП ≥3 месяцев, только Questionnaire, никакой выписки | 0/40 (все три 0)                                           | 0/20                                | Всегда MANUAL_REVIEW после submit, независимо от total и суммы. Анкета — только смета. |
| ИП ≥3 месяцев, 1–5 месяцев CSV                       | 0/40                                                       | 0/20                                | Всегда MANUAL_REVIEW. При месяце OUT-only учитывается 0 revenue, не «отсутствует».     |
| ИП ≥3 месяцев, 6–11 месяцев CSV                      | Считаем B1/B3; B2 если последние шесть месяцев подряд есть | Считаем I1/I2 по проверенным данным | Всегда MANUAL_REVIEW из-за неполной 12-месячной истории.                               |
| ИП 0–2 полных месяца, даже если есть CSV             | Альтернативный BUSINESS_START\_\*                          | 0/20                                | Всегда MANUAL_REVIEW, обычный GREEN запрещён.                                          |
| Человек без ИП                                       | Альтернативный BUSINESS_START\_\*                          | 0/20                                | Исключение STARTUP_AUTO_APPROVE_LIMIT и GOOD_BKI; иначе MANUAL.                        |

Если клиент выбрал «нет выписки», система не назначает автоматический
денежный лимит для действующего ИП: отправляет сотруднику с любой
запрошенной суммой. Лимит 200000 относится только к hasBusiness=false.
Questionnaire.monthlyRevenue и другие поля не используются в score.

При загрузке некорректного CSV сервер отвечает STATEMENT_UNREADABLE,
просит исправление (COLLECTING), без Score. Если подтверждение
невозможно, допустим переход через Questionnaire в MANUAL_REVIEW. При
противоречиях источников необходим INFO_REQUESTED или MANUAL_REVIEW, но
никогда автоматический RED по отсутствующим баллам.

# 8. Точные пределы Questionnaire и GoalAnswer

Все лимиты — предлагаемая серверная валидация MVP, не кредитные лимиты
банка. Ошибка диапазона → 400 VALIDATION_ERROR до расчёта; значение null
допустимо только если в question-sets.json unknownAllowed=true. Для
required=true, unknownAllowed=false null запрещено. Несколько целей ≤3;
не более одного ответа на questionId в своей группе, значения должны
соответствовать type.

| tender.term                                      | months        | 1…120 или null                                   | Не влияет на score                                                                                |

inventory.amount, cashgap.amount, tender.contract, marketing.budget. Для
equipment.price, unknownAllowed=true — 0 означает «цена пока неизвестна»
только если согласовано UX; в этой модели 0 допустим, но
авто-формирование точного предложения недопустимо. Для start.ownFunds=0
это осмысленное отсутствие собственных средств и не является ошибкой.
Любые nullable анкеты и GoalAnswer проверяются по официальному
question-sets.json, существующие id и field не меняем.

Общие технические пределы: не больше 3000 CSV-операций в demo-выписке и
20 МБ на файл — предложения для разработчика, НЕ часть утверждённого
mocks-contract.md; требуется отдельно согласовать, если хотят применять
на уровне API. Здесь не используются как балльные правила.

# 11. Псевдокод маршрутизации (без неявных решений)

\# Все баллы считаются только после успешной проверки шести
источников.  
if any_required_source_unavailable:  
status = "CHECKING"; nextAction = "RETRY_CHECKS"; score = None  
elif validated_stop_check:  
status = "REJECTED"; score = None \# RED-маршрут, но нет Score  
elif essential_input_incomplete_before_submit:  
status = "COLLECTING" \# либо INFO_REQUESTED по стадии  
score = None  
else:  
factors = calculate_contract_factors() \# сумма maxPoints ровно 100  
total = sum(f.points for f in factors)  
if hasBusiness is False:  
auto = (not any_manual and good_bki and requested_amount_is_explicit  
and 1 \<= requested_amount \<= STARTUP_AUTO_APPROVE_LIMIT)  
zone = "GREEN" if auto else "YELLOW"  
elif any_manual or monthsCovered \< 12 or business_age_months \< 12:  
zone = "YELLOW"  
elif total \< 40:  
zone = "RED"  
elif total \>= 80:  
zone = "GREEN"  
else:  
zone = "YELLOW"  
status = {"GREEN":"OFFER_READY", "YELLOW":"MANUAL_REVIEW",  
"RED":"REJECTED"}\[zone\]  
score = Score(total=total, zone=zone, factors=factors, flags=flags)
