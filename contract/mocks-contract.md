# Контракт: сервер ↔ заглушки внешних сервисов

Заглушки изображают внешние системы, к которым у нас нет доступа: реестр ФНС, бюро кредитных историй, приставов и т.д. В реальном банке эти данные у Альфы уже есть, поэтому в **границах системы** мы их не запрашиваем по-настоящему (так советовал куратор).

Все данные синтетические. Заглушки — один сервис на Python (FastAPI), папка `mocks/`, адрес внутри Docker `http://mocks:8090`. Данные заглушек — `mocks/data/`, тестовые клиенты и выписки — `tests/`.

**Кто делает:** владелец продукта (см. `README.md → Кто за что отвечает`). Готово: `mocks/` (сервис и его данные), `tests/` (клиенты, выписки, ожидаемые результаты). Ожидаемые результаты посчитаны по `scoring-model-v1.docx`.

## Общие правила

- Ответ — JSON. Деньги — целые рубли, даты — `YYYY-MM-DD`.
- Не нашли человека или ИП — `404` с `{ "code": "NOT_FOUND", "message": "..." }`.
- Для проверки сбоя: какие сервисы у какого тестового клиента отвечают `503`, указано в `mocks/data/failures.json` (сейчас — БКИ у клиента T10 «сервис недоступен» и паспорт `9941 000008`). Сервер должен показать «сервис временно недоступен» и сохранить заявку.
- Дата оценки в тестовых данных — 2026-10-24. Сервер берёт её из `EVALUATION_DATE` (см. `README.md`).
- Сервер ждёт ответа не дольше 5 секунд, потом считает, что сервис недоступен.

## Маршрут проверки человека без зарегистрированного ИП (согласовано БА)

- `hasBusiness = false` означает: человек ещё не зарегистрировал ИП. **Личный ИНН из 12 цифр допустим без записи в ЕГРИП**. Для полного набора проверок в этом сценарии личный ИНН передаётся на сервер; если клиент его не указал, сохранить заявку можно по существующему API, но до полного скоринга нужно запросить ИНН. Требование ИНН для полного скоринга — правило БА; делать его обязательным на этапе `POST /applications` без согласования изменения `openapi.yaml` нельзя.
- После согласия вызвать **все шесть проверок**: `/passport/check`, `/bki/report`, `/fssp/search`, `/bankruptcy/{inn}`, `/fns/tax-debt/{inn}` и `/fns/egrip/{inn}`. Сервисы банкротства и налогов принимают личный ИНН физлица, даже когда записи ЕГРИП нет. БКИ принимает тот же личный ИНН вместе с паспортными данными. Заглушки хранят синтетические ответы и для такого человека.
- Для `hasBusiness = false` ЕГРИП проверяет **отсутствие действующей регистрации**, а не наличие ИП. `404` с кодом `NOT_IP` означает ожидаемый ответ «сейчас не является ИП» → проверка ЕГРИП `OK`, корзина `NONE`, заявка продолжает путь. `status = TERMINATED` с `terminationDate` в прошлом также означает отсутствие действующего ИП → `NONE` (бывшая регистрация не используется для начисления бизнес-баллов). `status = ACTIVE` при `hasBusiness = false` — конфликт данных → `MANUAL`/уточнить `hasBusiness`, но **не** `STOP`. `404 NOT_FOUND` означает, что ИНН не удалось сопоставить с человеком; его нельзя приравнивать к `NOT_IP`: требуется исправление ИНН/проверка данных. Эта обработка описана в `openapi.yaml → /applications/{id}/consent`.
- Для `hasBusiness = true` поведение ЕГРИП остаётся исходным: `NOT_IP`/`NOT_FOUND` не подтверждает регистрацию ИП и ведёт к исправлению данных по текущему `openapi.yaml`.
- Если для стартапа не получен личный ИНН, запрещены автоматические `GREEN` и `RED` по неполным проверкам. Это запрос данных, а не наказание баллами.

## Запросы

### Реестр ФНС (ЕГРИП)

`GET /fns/egrip/{inn}`

```json
{
  "inn": "500100732259",
  "fullName": "Иванова Мария Сергеевна",
  "status": "ACTIVE",
  "registrationDate": "2022-03-15",
  "terminationDate": null,
  "okvedMain": { "code": "13.92", "name": "Производство готовых текстильных изделий, кроме одежды" },
  "okvedExtra": [],
  "region": "Санкт-Петербург"
}
```
`status`: `ACTIVE` (действует), `TERMINATED` (прекратил деятельность). ИНН принадлежит не ИП — `404` с кодом `NOT_IP`.

### Налоги

`GET /fns/tax-debt/{inn}`

```json
{ "inn": "500100732259", "hasDebt": false, "debtAmount": 0, "asOf": "2026-10-01" }
```

### Бюро кредитных историй

`POST /bki/report`
Запрос: `{ "passport": { "series": "4010", "number": "123456", "lastName": "...", "firstName": "...", "birthDate": "1988-05-20" }, "inn": "500100732259" }`

```json
{
  "reportAsOf": "2026-10-24",
  "loans": [
    {
      "type": "BUSINESS_LOAN",
      "openedAt": "2023-02-01",
      "amount": 1500000,
      "balance": 400000,
      "monthlyPayment": 52000,
      "status": "ACTIVE",
      "currentOverdueDays": 0,
      "overdues": [ { "date": "2024-07-10", "days": 12, "amount": 52000 } ]
    }
  ],
  "requestsLast30Days": 1
}
```
`type`: `BUSINESS_LOAN`, `CONSUMER_LOAN`, `MORTGAGE`, `CREDIT_CARD`, `CAR_LOAN`. `status`: `ACTIVE`, `CLOSED`. Нет истории — `loans: []` (это не ошибка).

`reportAsOf` — **обязательное новое поле**, дата формирования отчёта (`YYYY-MM-DD`). Дата не должна быть позже даты оценки. По допущению команды, если `reportAsOf` старше даты оценки более чем на 30 календарных дней, ставим `MANUAL`, но **не** `STOP` и **не** «нет кредитной истории». Если дата отсутствует/невалидна — нарушение контракта ответа, требуется повтор/ручная обработка, нельзя считать такой отчёт актуальным. Дата оценки определяется сервером в момент расчёта и сохраняется вместе с результатом.

Для `hasBusiness = false` запрос по личному ИНН без записи ЕГРИП возвращает обычный отчёт БКИ (в том числе `loans: []`). Это не `404 NOT_IP`.


### Приставы (ФССП)

`POST /fssp/search` — ищет по ФИО и дате рождения; ФИО сравниваются так же, как в паспортной проверке (регистр, пробелы, Ё/Е не важны).
Запрос: `{ "lastName": "...", "firstName": "...", "middleName": "...", "birthDate": "1988-05-20" }`

```json
{
  "proceedings": [
    { "number": "12345/26/78001-ИП", "startedAt": "2026-04-02", "subject": "TAX", "amount": 85000, "propertyArrest": true, "status": "ACTIVE" }
  ]
}
```
`subject`: `TAX`, `LOAN`, `UTILITIES`, `FINE`, `OTHER`. `status`: `ACTIVE`, `FINISHED`.

### Реестр банкротств

`GET /bankruptcy/{inn}`

```json
{ "inn": "500100732259", "inProcedure": false, "stage": null, "startedAt": null, "completedAt": null }
```
`stage`: `null`, `RESTRUCTURING`, `REALIZATION`, `COMPLETED`.

**Новое поле** `completedAt`: `YYYY-MM-DD` или `null`. Оно заполняется, если `stage = COMPLETED`, и означает дату завершения процедуры, а не дату признания банкротом.

| Состояние | `inProcedure` | `stage` | `startedAt` | `completedAt` | Проверка |
| --- | --- | --- | --- | --- | --- |
| Банкротства нет | `false` | `null` | `null` | `null` | `NONE` |
| Действующая реструктуризация | `true` | `RESTRUCTURING` | Дата | `null` | `STOP` по ранее предложенной модели (допущение, не прямой запрет закона на любой кредит) |
| Действующая реализация имущества | `true` | `REALIZATION` | Дата | `null` | `STOP` по ранее предложенной модели |
| Завершено менее пяти лет назад | `false` | `COMPLETED` | Дата или `null` | Дата | `MANUAL` |
| Завершено пять лет назад или раньше | `false` | `COMPLETED` | Дата или `null` | Дата | `NONE` по этому правилу (история не скрывается от сотрудника) |
| Неполный/противоречивый ответ | Любое | Несогласованное | Любое | Несогласованное | `MANUAL` / повтор получения данных; автоодобрение запрещено |

**Правило пяти лет:** сравнить календарные даты. Пятилетие истекает в дату `completedAt + 5 календарных лет`. Если `evaluationDate < anniversary`, то `MANUAL`; при `evaluationDate >= anniversary` — `NONE` по проверке пятилетнего срока. Например, при дате оценки 2026-10-24 завершение 2021-10-25 означает `MANUAL`, а 2021-10-24 — срок уже истёк. Дата завершения в будущем, а также `completedAt < startedAt` (если начало известно), — противоречивый ответ.

**Почему не `STOP` при завершённом банкротстве:** ст. 213.30 Закона № 127-ФЗ требует в течение пяти лет сообщать о банкротстве при принятии кредитных и заёмных обязательств, но не устанавливает абсолютного запрета брать кредит. Ст. 216 регулирует дополнительные последствия банкротства именно ИП, включая пятилетние ограничения и исключения по п. 5; полей для определения вида прежнего статуса, содержания судебного акта и применимости исключений здесь нет. Поэтому `MANUAL` — допущение внутреннего процесса, чтобы сотрудник проверил обстоятельства.

Источники закона (проверено на 24.10.2026): [ст. 213.30, Закон № 127-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_39331/15bac90772e695baab0ffa86106dfd11c02e7802/); [ст. 216, Закон № 127-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_39331/172be73862055bd14886b44f702a4f7fceb7f94c/).

**Ограничение полей:** контракт не различает «банкротился гражданин» и «банкротился зарегистрированный ИП». Нельзя из одного `stage = COMPLETED` автоматически выводить законность/незаконность новой регистрации ИП. Такой случай требует сотрудника при незавершённом пятилетнем сроке.


### Проверка паспорта — вариант Б (согласовано БА)

`POST /passport/check` — **внутренний запрос бэкенда к заглушке**, не новый публичный маршрут `/api`.

**Запрос:** из уже имеющегося `openapi.yaml → components.schemas.Passport`; `middleName` необязателен и может отсутствовать.

```json
{
  "series": "4010",
  "number": "123456",
  "lastName": "Иванова",
  "firstName": "Мария",
  "middleName": "Сергеевна",
  "birthDate": "1988-05-20",
  "issueDate": "2018-06-14"
}
```

**Ответ, если документ действителен и данные владельца совпали с независимой записью заглушки:**

```json
{
  "valid": true,
  "reason": null,
  "holderMatch": true,
  "mismatchFields": []
}
```

**Поля ответа:**

| Поле | Тип | Точное значение |
| --- | --- | --- |
| `valid` | boolean | Признак действительности **этого** синтетического номера паспорта |
| `reason` | `null` или `LOST`, `EXPIRED`, `REPLACED` | При `valid=true` обязательно `null`; при `valid=false` — один из трёх кодов |
| `holderMatch` | `true`, `false`, `null` | `true`: все сведения совпали с независимой записью; `false`: есть хотя бы одно несовпадение; `null`: надёжное сопоставление невозможно или документ недействителен |
| `mismatchFields` | array[string] | Только `LAST_NAME`, `FIRST_NAME`, `MIDDLE_NAME`, `BIRTH_DATE`, `ISSUE_DATE`. Упорядочивать именно в этом порядке. Массив непустой **только** при `holderMatch=false` |

**Обязательное ограничение:** эталонные сведения о владельце должны храниться в независимой синтетической записи `mocks/data/`, а не создаваться на лету из поступившего запроса. Не возвращать эталонные ФИО или даты в ответе. При поиске записи используется только пара `series + number`, а не переданные ФИО.

**Алгоритм сопоставления (одинаковый результат на одинаковых данных):**

1. Проверить наличие `series`, `number`, `lastName`, `firstName`, `birthDate`, `issueDate` и их форматы по `openapi.yaml → Passport`; `middleName` необязателен. Некорректный запрос → HTTP 400 с `{ "code": "VALIDATION_ERROR", "message": "Некорректные поля паспорта" }`, без скоринговой корзины.
2. Найти синтетический паспорт **по точным строковым** `series` и `number` (ведущие нули сохранять). Если эталонная запись о документе не найдена → HTTP 404 `NOT_FOUND`; **не объявлять документ недействительным**. Сервер фиксирует `PASSPORT_HOLDER_UNKNOWN → MANUAL`, без автоодобрения; не путать с `valid=false`.
3. Если в записи `valid=false` и `reason` равно `LOST`/`EXPIRED`/`REPLACED` → вернуть `{ "valid": false, "reason": "LOST", "holderMatch": null, "mismatchFields": [] }` (код причины фактический) → `PASSPORT_INVALID`, корзина `STOP`. Совпадение владельца после этого не вычисляется.
4. Если документ `valid=true` и есть все пять эталонных атрибутов владельца (для отчества допустимо подтверждённое отсутствие), сравнить строки ФИО после нормализации: `trim`, схлопывание последовательностей пробельных символов до одного пробела, верхний регистр, замена `Ё` на `Е`; другие символы не изменять. `birthDate` и `issueDate` сравнивать как точные строки `YYYY-MM-DD`. В **запросе** `middleName` может отсутствовать, быть `null`, пустой строкой либо пробелами — все четыре варианта означают «отчество не указано». В **эталонной записи** ключ `middleName` должен присутствовать: `null` или пустая строка означают подтверждённое отсутствие отчества, а **отсутствующий ключ** означает нехватку сведений (`holderMatch=null`). Если только с одной стороны отчество подтверждённо отсутствует, это `MIDDLE_NAME` в списке несовпадений.
5. Сформировать `mismatchFields` по отличиям в фиксированном порядке `LAST_NAME`, `FIRST_NAME`, `MIDDLE_NAME`, `BIRTH_DATE`, `ISSUE_DATE`. Если пусто → `holderMatch=true`, иначе `false` → `PASSPORT_HOLDER_MISMATCH`, корзина `MANUAL`.
6. Если `valid=true`, но отсутствует хотя бы один **обязательный эталонный атрибут** (`lastName`, `firstName`, `birthDate`, `issueDate`) или в эталоне отсутствует ключ `middleName` (сведения неизвестны) → `holderMatch=null`, `mismatchFields=[]` → `PASSPORT_HOLDER_UNKNOWN`, корзина `MANUAL`. Не превращать неизвестное в совпадение.
7. Любое противоречие ответа, например `valid=true, reason=LOST`, `holderMatch=false, mismatchFields=[]`, `holderMatch=true` с непустым массивом или `valid=false, reason=null`, означает ошибку контракта `PASSPORT_CHECK_CONFLICT`; безопасная обработка — `MANUAL` и повтор/диагностика, но **не STOP по недостоверному ответу**. Заглушка сама обязана формировать только валидные комбинации.
8. HTTP 503 или тайм-аут более 5 секунд → `CheckResult.state=ERROR`, `CHECKING`, `nextAction=RETRY_CHECKS`. Это **не** `MANUAL`, `MINUS` или `STOP`.

**Корзины для паспорта:**

| Проверка `code` | Условие | `basket` | `state` | Дальнейшее действие |
| --- | --- | --- | --- | --- |
| `PASSPORT_VALID` | `valid=true`, `holderMatch=true` | `NONE` | `OK` | Продолжить проверки |
| `PASSPORT_INVALID` | `valid=false`, `reason=LOST/EXPIRED/REPLACED` | `STOP` | `FAIL` | `REJECTED` (внутреннее правило MVP) |
| `PASSPORT_HOLDER_MISMATCH` | `valid=true`, `holderMatch=false` и есть несовпавшие поля | `MANUAL` | `WARNING` | Завершить остальные проверки, после submit — `MANUAL_REVIEW` |
| `PASSPORT_HOLDER_UNKNOWN` | `valid=true`, `holderMatch=null` либо 404 при неизвестной записи | `MANUAL` | `WARNING` | Завершить остальные проверки, после submit — `MANUAL_REVIEW` |
| `PASSPORT_CHECK_CONFLICT` | Невалидный/противоречивый JSON | `MANUAL` | `WARNING` | Диагностика / ручной разбор; без автоодобрения |
| `PASSPORT_CHECK_UNAVAILABLE` | HTTP 503, сетевой сбой или тайм-аут | без корзины; `state=ERROR` | `ERROR` | Остаться в `CHECKING` и предложить повтор |

При одновременно полученных разных сигналах корректного ответа приоритет: `STOP > MANUAL > NONE`. Проверка формата паспорта до согласия — валидация ввода, не `STOP`. Сопоставление ФИО с ЕГРИП **сохраняется отдельным правилом** и не заменяется `holderMatch`.

**Границы модели:** реального обращения к МВД или установления личности человека перед экраном нет. Совпадение с синтетической записью лишь демонстрирует сверку данных. Не рассчитывать `EXPIRED` самостоятельно по дате выдачи: для MVP это статус эталонной записи, а не дополнительная вычисляемая норма.

**Минимальные тесты:**

| Сценарий | Изменение запроса/эталона | Ожидаемое |
| --- | --- | --- |
| Полное совпадение | Все данные совпадают | `PASSPORT_VALID / NONE` |
| Ошибка фамилии | Отличается `lastName` | `PASSPORT_HOLDER_MISMATCH / MANUAL`, `mismatchFields=["LAST_NAME"]` |
| Другая дата рождения | Отличается `birthDate` | `MANUAL`, `["BIRTH_DATE"]` |
| Другая дата выдачи | Отличается `issueDate` | `MANUAL`, `["ISSUE_DATE"]` |
| Недействительный паспорт | `valid=false`, `reason=LOST` | `PASSPORT_INVALID / STOP` |
| Нет подтверждённой записи владельца | `holderMatch=null`, `mismatchFields=[]` | `PASSPORT_HOLDER_UNKNOWN / MANUAL` |
| Недоступность сервиса | HTTP 503 | `CHECKING / RETRY_CHECKS`, без решения |

## Формат выписки

Клиент загружает файл, сервер его разбирает. Генерирует тестовые выписки заглушка (`tests/statements/{inn}.csv`), скачать — `GET /api/demo/statements/{inn}`.

- CSV, кодировка UTF-8, разделитель `;`, первая строка — заголовки.
- Операции минимум за 12 месяцев (меньше — сервер ставит предупреждение).

| Колонка | Пример | Что значит |
| --- | --- | --- |
| `date` | `2026-03-12` | Дата операции |
| `amount` | `45000` | Сумма, целые рубли, всегда положительная |
| `direction` | `IN` | `IN` — поступление, `OUT` — списание |
| `counterparty` | `ООО Модный дом` | Контрагент |
| `counterpartyInn` | `7801234567` | ИНН контрагента (может быть пустым) |
| `purpose` | `Оплата по договору поставки №15` | Назначение платежа |

Пример:
```
date;amount;direction;counterparty;counterpartyInn;purpose
2026-03-01;120000;OUT;ИП Петров;780212345678;Аренда цеха за март
2026-03-03;45000;IN;ООО Модный дом;7801234567;Оплата по договору поставки №15
2026-03-05;560000;OUT;Зарплатный проект;;Выплата заработной платы за февраль
```

**Категории расходов**, по которым сервер раскладывает списания: `RENT` (аренда), `SALARY` (зарплата), `MATERIALS` (материалы, товар), `TAXES` (налоги и взносы), `LOAN_PAYMENTS` (платежи по кредитам), `OTHER` (прочее). Поступления: `CUSTOMER` (от покупателей), `ACQUIRING` (эквайринг), `OTHER_IN`.

### Классификация поступлений (`IN`): точные правила для бэкенда

Это **правила команды для синтетического CSV**, а не универсальный банковский классификатор. В скоринге **не используются категории, предложенные ИИ**. Категория для каждой строки определяется только полями `direction`, `purpose`, `counterpartyInn`; `counterparty` сохраняем как описание, но не используем для подтверждения выручки.

**1. Нормализация текста `purpose` (строго в этом порядке):**

1. Привести Unicode-текст к нижнему регистру (`casefold`), заменить `ё` на `е`.
2. Заменить каждую непрерывную последовательность символов, **кроме** русских букв `а-я`, латинских `a-z` и цифр `0-9`, на один пробел.
3. Удалить пробелы по краям; несколько пробелов внутри заменить одним. Проверять только **полные слова/фразы** с границей по пробелу или краю строки, а не подстроку внутри другого слова.
4. `counterpartyInn` для правила CUSTOMER считается заполненным, если после удаления пробелов содержит **ровно 10 или 12 цифр**. Контрольные суммы ИНН контрагента для классификации не проверяются (это допущение MVP).

**2. Категории применяются по приоритету; первое совпадение завершает проверку:**

| Приоритет | Условие при `direction = IN` | Категория |
| --- | --- | --- |
| 1 | Нормализованный `purpose` содержит хотя бы одну фразу из списка *исключений* ниже | `OTHER_IN` |
| 2 | Содержит хотя бы одну фразу из списка *эквайринга* ниже | `ACQUIRING` |
| 3 | Содержит хотя бы одну фразу из списка *платежей покупателей* ниже **и** `counterpartyInn` заполнен по правилу выше | `CUSTOMER` |
| 4 | Ни один пункт не сработал, `purpose` пустой или ИНН покупателя отсутствует/неподходящего формата | `OTHER_IN` |

**Список исключений (любой из них принудительно даёт `OTHER_IN`):**

`возврат`, `сторно`, `отмена операции`, `refund`, `reversal`, `возврат налога`, `возмещение налога`, `зачисление кредита`, `выдача кредита`, `кредитные средства`, `заем`, `займ`, `договор займа`, `перевод собственных средств`, `перевод между своими счетами`, `перевод между счетами`, `внутренний перевод`, `пополнение счета`, `внесение наличных`, `взнос наличных`, `депозит`, `вклад`, `субсидия`, `грант`, `страховое возмещение`, `продажа основных средств`, `продажа оборудования`, `возврат займа`.

Примечание: точная фраза `возврат` проверяется как **слово**. Поэтому `возврата` без отдельного правила не совпадает: это сознательно ограниченный словарь MVP. Нераспознанные варианты безопасно попадают в `OTHER_IN`, но при появлении новых словоформ список нужно согласованно расширять.

**Список эквайринга (`ACQUIRING`):**

`эквайринг`, `acquiring`, `реестр операций по картам`, `выплаты по операциям с картами`, `зачисление по операциям с картами`, `возмещение по операциям с картами`, `сбп оплата товаров`, `сбп оплата услуг`.

Одинокое слово `сбп`, а также поступление от банка без явного назначения эквайринга **недостаточно** для этой категории.

**Список платежей покупателей (`CUSTOMER`):**

`оплата по договору`, `оплата по счету`, `оплата за`, `оплата товара`, `оплата товаров`, `оплата услуг`, `оплата работ`, `аванс по договору`, `предоплата по договору`, `выручка от реализации`, `поступление от покупателя`, `платеж покупателя`, `оплата по заказу`.

Слово «оплата» само по себе недостаточно. Если описание подходит под `CUSTOMER`, но `counterpartyInn` пуст или неправильной длины, категория — `OTHER_IN`, не `CUSTOMER`.

**3. Какие поступления участвуют в скоринге:**

- Операционная выручка месяца = сумма `amount` по строкам `IN` с категорией `CUSTOMER` **или** `ACQUIRING`.
- `OTHER_IN` **не включается** в операционную выручку. Все категории `OUT` учитываются в денежных расходах по прежней схеме.
- В `StatementSummary.monthly[].income` и `avgMonthlyIncome` записывать именно операционную выручку, а не сумму всех `IN`.
- Для контроля сохранить во внутренней обработке сумму всех входящих операций и сумму `OTHER_IN`; если `sum(OTHER_IN) * 100 > sum(all IN) * 20`, добавить `warnings` с текстом `Более 20% входящих операций не удалось подтвердить как выручку` и обязательный `MANUAL`. Если сумма всех входящих операций = 0, долю не вычислять; поставить предупреждение `Нет подтверждённых поступлений` и `MANUAL`. Порог 20% — **допущение команды**.
- Категоризация не исправляет и не удаляет исходные CSV-строки, порядок обработки строк не влияет на результат. Если две строки полностью совпали, обе учитываются: в контракте нет идентификатора банковской операции для безопасной дедупликации.

**4. Контрольные примеры классификации:**

| `direction` | `purpose` | `counterpartyInn` | Результат |
| --- | --- | --- | --- |
| `IN` | `Оплата по договору поставки №15` | `7801234567` | `CUSTOMER` |
| `IN` | `Эквайринг. Реестр операций по картам` | пусто | `ACQUIRING` |
| `IN` | `Зачисление кредита по договору` | `7701234567` | `OTHER_IN` |
| `IN` | `Возврат оплаты по договору` | `7701234567` | `OTHER_IN` |
| `IN` | `Оплата по счету` | пусто | `OTHER_IN` |
| `IN` | `СБП перевод` | пусто | `OTHER_IN` |
| `IN` | `Оплата услуг` | `7701234567` | `CUSTOMER` |

### Полнота выписки, пропущенные месяцы и расчётный период

**Техническая полнота** — наличие записей за календарные месяцы. **Документальная полнота** (действительно ли банк выгрузил все операции за каждый день) по имеющимся шести CSV-колонкам **не подтверждается**. Эти понятия не смешивать; автоматическое распознавание пропущенных операций невозможно без дополнительных банковских метаданных.

Правила для MVP (допущения команды):

1. `evaluationDate` — дата расчёта на сервере (не системная дата клиента). **Текущий неполный календарный месяц исключаем** из всех факторов оборота и расчёта `monthsCovered`.
2. Анализируем **12 последних полностью завершившихся календарных месяцев** до месяца `evaluationDate` включительно по границам месяцев. Например, 24.10.2026 окно: с 01.10.2025 по 30.09.2026 включительно.
3. Строки раньше начала окна или позже его конца не влияют на расчёт скоринга; будущая дата строки (позже `evaluationDate`) — ошибка формата. В `StatementSummary` отражаем именно рассчитанное окно и операции из него.
4. Для каждого месяца окна отмечаем `present = true`, если есть хотя бы **одна** корректная CSV-операция `IN` или `OUT`. **Нет ни одной строки → месяц пропущен**. Не подставлять нулевые поступления или расходы и не трактовать отсутствие строк как доказанный нулевой оборот.
5. `monthsCovered` = количество присутствующих месяцев в 12-месячном окне, от 0 до 12. `monthly[]` содержит **только присутствующие месяцы**, отсортированные по `YYYY-MM`, с суммами операционных поступлений и списаний. `periodFrom` и `periodTo` — минимальная/максимальная дата корректных операций **в окне**, а не придуманные границы покрытия. Если ни одной операции нет, вернуть `STATEMENT_UNREADABLE` (вместо фиктивных дат).
6. `avgMonthlyIncome` = `sum(monthly[].income)/monthsCovered`, `avgMonthlyExpense` — аналогично. **Деление только на число присутствующих месяцев**, округление до целого рубля `ROUND_HALF_UP`; при `monthsCovered = 0` файл не проходит валидацию. При пропусках оба средних значения остаются предварительными и включается `MANUAL`.
7. Любой отсутствующий месяц добавить в `StatementSummary.warnings` отдельной строкой вида `Нет операций за 2026-02 — период не подтверждён`. При `monthsCovered < 12` также добавить `Выписка подтверждает N из 12 календарных месяцев`; такая выписка не может автоматически получить `GREEN`. При 6–11 месяцах доступные финансовые данные можно рассчитать для сотрудника; при 1–5 — факторы, требующие 6 месяцев, не оцениваем. Менее 3 месяцев — крайний случай из `tests/statements/`, не автоматически кредитный отказ.
8. Если в месяце есть операции только `OUT`, его `income = 0`, `expense > 0` и месяц **считается присутствующим**. Если есть только `IN`, его `expense = 0`. Это не признак ошибки само по себе.
9. Не включать в `monthly[]` месяцы только потому, что календарь между `periodFrom` и `periodTo` их содержит. Их отсутствие отражается предупреждением, не нулевым значением.
10. Для данных за 12 месяцев есть только *техническая полнота*, а не доказательство отсутствия удалённых строк. Сохранить этот риск как ограничение MVP; при переходе к реальным банковским выпискам понадобится подтверждение периода выгрузки.

**Правила чтения CSV:** UTF-8, допускается BOM; разделитель `;`; набор заголовков **ровно** `date`, `amount`, `direction`, `counterparty`, `counterpartyInn`, `purpose` (порядок колонок может быть любым); дата в формате `YYYY-MM-DD`; `amount` — целое строго положительное число без пробелов, запятых и копеек; `direction` — только `IN` или `OUT`. Пустые строки разрешены и игнорируются. Ошибка обязательной колонки, даты, суммы или направления → `STATEMENT_UNREADABLE` без частичного расчёта. Пустой `counterpartyInn` допустим. Иные дополнительные CSV-колонки не принимаются без изменения контракта. Если `counterpartyInn` непустой, но не состоит из 10/12 цифр, строку не отклоняем: для `IN` он не может подтвердить `CUSTOMER`.

**Контрольный тест пропуска:** дата оценки 2026-10-24, операции есть в октябре 2025 — январе 2026 и марте — сентябре 2026, но нет ни одной операции в феврале 2026. Тогда `monthsCovered = 11`, `monthly[]` не содержит `2026-02`, в `warnings` указать февраль и 11/12, автоматическое `GREEN` запрещено независимо от баллов.


Плохие файлы для краевых случаев (тоже в `tests/statements/`): пустой, не CSV, с другими колонками, меньше 3 месяцев.

## Формат `industries.json`

Файл для синтетических данных прототипа. **Нельзя выдавать его числа за фактическую статистику ФНС или Росстата.** Точная структура лежит в отдельном прилагаемом `industries.json`.

Корень JSON: `{ "version": "0.2", "industries": [ ... ] }`; `industries` — массив уникальных объектов, отсортированных по `okvedCode`.

| Поле каждой отрасли | Тип / допустимые значения | Правило |
| --- | --- | --- |
| `okvedCode` | string | ОКВЭД из справочника (например, `13.92`); ключ уникален |
| `name` | string | Отображаемое название отрасли |
| `riskTier` | `LOW`, `MEDIUM`, `HIGH` | Экспертная категория, только 4 балла `INDUSTRY_BASE_RISK` |
| `growthYoYPercent` | number или `null` | Изменение отраслевой выручки за год в процентах; отрицательное число = падение |
| `closureSharePercent` | number от 0 до 100 или `null` | Доля прекративших деятельность ИП; для MVP синтетическая |
| `dataAsOf` | `YYYY-MM-DD` | Дата, к которой отнесены отраслевые показатели |
| `sourceUrl` | URL или `null` | `null` для синтетических данных, URL только для реальной публикации |
| `sourceType` | `SYNTHETIC` или `OFFICIAL` | `SYNTHETIC` обязательно для демонстрационных цифр |
| `scope` | `RUSSIA_OKVED_EXACT` или `RUSSIA_OKVED_2DIGIT` | Уровень отраслевой детализации; для регионального анализа потребуется расширение контракта |
| `seasonality` | `LOW`, `MEDIUM`, `HIGH`, `UNKNOWN` | Для информации/сметы; напрямую баллы не начисляет |
| `typicalExpenses` | массив `{category, sharePercent}` | Категории расходов из данного файла; доли 0–100, сумма долей ровно 100, если массив не пустой; только для сметы |
| `typicalBreakEvenMonths` | положительное целое или `null` | Типичная окупаемость; сравнивается с прогнозом клиента **информационно, без баллов** |

Фактор отрасли считается только при наличии соответствующих значений. Для `growthYoYPercent = null` или `closureSharePercent = null` соответствующий фактор имеет 0 баллов с признаком отсутствия данных и `MANUAL`. При отсутствии кода в справочнике — `MANUAL`, не угадывать отрасль.

Поиск ОКВЭД: сначала точное совпадение с `okvedMain.code` (или `plannedOkved` у стартапа). Если не найдено — разрешён fallback **только на двухзначную группу** (`47.76` → `47`) при наличии объекта с `okvedCode = "47"` и `scope = RUSSIA_OKVED_2DIGIT`. Если не найдена и группа — `MANUAL`. ИИ не выбирает код сам для решения; предложенный ИИ код должен быть подтверждён клиентом.

Для `start.breakEven` (`question-sets.json`, `field = expectedBreakEvenMonths`), а также `location.breakEven`: если прогноз клиента и `typicalBreakEvenMonths` положительные целые, вычисляем разницу `clientMonths - typicalBreakEvenMonths` и показываем сравнение «быстрее / на уровне / медленнее типичной окупаемости». **Ни в `BUSINESS`, ни в `OWNER`, ни в `IDEA`, ни в `INDUSTRY` этот ответ напрямую или косвенно баллы не добавляет**. Если значение отсутствует — сравнение не выполняется. Типичный срок окупаемости — синтетический ориентир, не банковская гарантия.

Нормативная история налоговых долгов **не добавляется**: утверждённого фактора «недавно закрыл налоговый долг» в модели нет.

Паспортная проверка — согласованный **вариант Б**; весь запрос, ответ, правила сравнения и тесты описаны в разделе `Проверка паспорта`.
