# Контракт команды — «Умный финансовый навигатор для ИП»

Версия 0.9 · 25 октября 2026 · **Согласовано владельцем продукта. Можно передавать фронту и бэку.**

Контракт — это договорённость, **как части проекта разговаривают друг с другом**: какие запросы, какие поля, какие статусы. Каждый делает свою часть строго по нему, поэтому при сборке всё сходится.

Продукт описан в концепции (`Концепция v2 — навигатор для ИП.docx`). Контракт — это «как именно» для кода.

## Три папки проекта

| Папка | Что внутри | Кто меняет |
| --- | --- | --- |
| `contract/` | Этот контракт: правила, запросы, справочники. Все файлы в одной папке, без вложенных | Владелец продукта (по согласованию) |
| `mocks/` | Сервис-заглушка внешних проверок и его данные (`mocks/data/`) | Владелец продукта |
| `tests/` | Тестовые клиенты, их выписки, ожидаемые результаты, автотесты и скрипты, которые всё это пересчитывают | Владелец продукта |

## Кто за что отвечает

| Кто | Папка | Что делает |
| --- | --- | --- |
| Человек 1 — фронт | `frontend/` | React. Воронка клиента, кабинет сотрудника |
| Человек 2 — бэк | `backend/` (кроме `backend/app/ai/`) | Python, FastAPI. Заявки, статусы, расчёт, вызов заглушек и ИИ |
| Человек 3 — БА | `docs/` (документы для сдачи) | Документы бизнес-анализа. Модель баллов уже лежит в `contract/` |
| Человек 4 — ИИ и сборка | `backend/app/ai/`, корень (`docker-compose.yml`, `README.md`, `THIRD_PARTY_NOTICES`) | Промпты, модель, Docker, сдача |
| Владелец продукта | `contract/`, `mocks/`, `tests/` | Решения по продукту, согласование правок. Заглушки и тестовые данные готовы (см. `mocks/README.md`, `tests/README.md`) |

Меняешь только свою папку. Чужие — только читать.

## Общие правила данных

1. **Деньги** — целые рубли (`integer`), без копеек.
2. **Даты** — `YYYY-MM-DD`, дата и время — ISO 8601 с часовым поясом.
3. **Названия полей** — `camelCase` в API, как в `openapi.yaml`.
4. **Ошибки** всегда одного вида: `{ "code": "...", "message": "...", "details": {} }`. Коды — в `openapi.yaml` (`ErrorCode`). Сайт показывает `message`, логика смотрит на `code`.
5. **Входа и паролей нет** (совет куратора). Клиент работает с заявкой по её `id`. Кабинет сотрудника — по адресу `/staff`, запросы `/api/staff/...`.
6. **Клиенту не показываем баллы и формулы.** Баллы видит только сотрудник.
7. **ИИ ничего не решает.** Решение, баллы и цифры сметы — только правила на сервере.
8. **Без ИИ всё работает.** Если `aiAvailable: false`, сайт показывает кнопки и форму вместо чата.

## Границы текущей версии

- **Конструктора «Проверить свой бизнес» нет** — решение владельца продукта. Для проверки — 10 тестовых клиентов (`GET /api/demo/clients`).

- Согласованы: паспортная заглушка (вариант Б), пятигодичный `MANUAL` после завершённого банкротства, личный ИНН для стартапа, детерминированная классификация поступлений, техническая полнота выписки, формат синтетического отраслевого справочника, пять редакций вопросов. Все прежние `id` и `field` вопросов сохранены.
- Согласованы с фронтом: типизированная схема `GET /question-sets`, повторная заявка (`POST /applications` → `200` с открытой заявкой), передача сотруднику при непонятой цели (`POST /applications/{id}/handoff`), честное отображение проверок без выдуманного прогресса, новый вопрос `inventory.items`.
- Стартап: одно правило — автоодобрение только при сумме до порога и хорошей личной кредитной истории, иначе сотрудник (`scoring-clarifications.md`, раздел 7).
- В `StaffApplicationCard.breakEvenComparisons` сотрудник видит сравнение заявленного прогноза и отраслевого ориентира. **Ни слова клиента, ни это сравнение не изменяют баллы.**
- **Модель баллов утверждена** — `scoring-model-v1.docx`: BUSINESS 40 + OWNER 30 + IDEA 20 + INDUSTRY 10, зоны GREEN от 80 / YELLOW / RED до 40, стартап — автоодобрение до `STARTUP_AUTO_APPROVE_LIMIT = 200000` при хорошей кредитной истории. Все вопросы из раздела 12 модели приняты как предложено БА. Пороги бэк держит в настройках, а не в коде.
- **Правила продуктов утверждены** — `product-rules-v1.md`: ключевая ставка 14% + надбавка по продукту, отсрочка 3 мес. для новой точки и стартапа, безопасный платёж ÷ 1,3, «Начать меньше» 60%, до 3 предложений. Все значения — настройки сервера.
- **Дата оценки для демо.** Сервер берёт дату оценки из переменной `EVALUATION_DATE` (`YYYY-MM-DD`); если её нет — текущую дату. В Docker для демо и жюри: `EVALUATION_DATE=2026-10-24`. Иначе через несколько дней тестовые выписки и отчёты БКИ «устареют» и все клиенты уйдут к сотруднику.
- **Ожидаемые результаты** для каждого тестового клиента — `tests/expected-results.json` (в репозитории, папка владельца продукта). Бэк сверяет с ним свой расчёт.

## Как менять контракт

1. Нашёл, что в контракте чего-то не хватает или противоречие — **не придумывай своё**, напиши в общий чат.
2. Изменение согласуют те, кого оно касается (например, фронт и бэк для `openapi.yaml`).
3. Меняем файл, повышаем версию в начале этого README и пишем строку в «Историю изменений».

## Приоритеты

В `openapi.yaml` у каждого запроса есть пометка `x-priority`:
- `must` — обязательно, без этого нет основного сценария;
- `should` — желательно;
- `could` — если успеем.
